# 踩过的坑

按「现象 → 怎么判断的 → 现在的方案 / 还没解决的部分」记。日志片段都做了脱敏
(地址、账号、设备 ID 换成占位值),错误码和关键字保留原样。

## 1. 校园网:能扫描到,板子却连不上

**现象.** C5 扫描能看到同一 SSID 的 2.4 GHz 和 5 GHz 两个 AP,选 802.1X PEAP 认证时一直失败,
日志里是 `reason=23`(802.11 association 被 AP 拒绝)。同一个位置,手机和电脑能正常连。

**怎么判断的.** 频段兼容和 802.1X 认证是两个独立关卡:扫描到只能说明射频通,
`reason=23` 说明关联阶段就被拒了。换开放网络(`CAMPUS_WIFI_OPEN=y`)后,板子在 5 GHz
信道 44 关联成功并拿到 IPv4 —— 说明硬件和频段没问题,卡在认证环节。具体是哪一项
(证书校验、外层身份、RADIUS 域、还是 AP 侧限制了这类客户端)没定位到。

**现在的方案.**
- 部署改用**开放接入**的网络,认证交给 Captive Portal。
- Portal 探测收到 `HTTP 302`,同一轮里板子并没有发出网页登录请求,但 MQTT TLS 连接、订阅和
  消息往返都完成了 —— 说明该网络对这个客户端放行,不需要走 Portal 登录。
- 换到别的网络必须**现场实测**:Portal 探测通过不等于一定放行,PEP 认证通过也不等于能出去。

**没解决的部分.** 在需要 802.1X 的网络里怎么让 C5 稳定接入。想试的方向:
换 RADIUS 证书校验方式、抓 AP 侧日志看为什么 `reason=23`、或者干脆加个随身路由做桥接。

## 2. 手机显示「已连接」,按下去却没动作

**现象.** 手机 App 首页显示已连接,点「远程启动」,舵机不动,也看不到回执。

**怎么判断的.** 这里有**三个独立状态**容易被混成一个:

1. 手机连上了 Broker;
2. C5 在线(订阅成功 / 有 30 秒心跳);
3. C5 真的执行了动作并回了回执。

App 原来只显示第 1 个,所以「已连接」≠「能按」。诊断通道收到公网 `pong` 能证明手机到 Broker
的链路能往返,但证明不了板子在听。另外在一次公网测试里,手机走蜂窝网络连测试 Broker 的 **IPv6**
地址时出现了 `ECONNREFUSED` —— 换 IPv4 就好,属于测试环境问题,不是固件的事。

**现在的方案.**
- 公网 ping/pong **只用于联调**,正式通道走带账号和主题 ACL 的 TLS Broker,两套分开;
- 用四段证据定位:订阅成功日志 → `online` → 30 秒心跳 → 按时间戳匹配的 `done`/`failed`;
- 固件加短指令有效期(20 s)、5 秒冷却、NVS 持久去重,指令 **关闭 Retain**;
- 手机端回执超时显示「结果未知」,不自动重发。

**没解决的部分.** 正式按钮曾出现过「点了,舵机没动」,单次故障的根因没确认。
再遇到按这个顺序查:C5 串口有没有 `MQTT subscription acknowledged` → 有没有收到那条指令 →
有没有回 `done`。收到 `done` 但舵机没动,就是机械或供电问题,用 `p`/`r` 单独试。

## 3. ESP-IDF 环境、烧录和串口容易互相混淆

**现象 A.** 换过 ESP-IDF 的 Python 环境之后,`idf.py app-flash` 直接被拒绝,报解释器路径不对。

**原因.** 旧构建缓存里记着上一次的 Python 解释器绝对路径。

**处理.** `idf.py fullclean` 后重新构建。首次配置时用同一套终端环境,之后增量编译就不会踩。

**现象 B.** 烧录通过了哈希校验,但打开串口读不到日志,或者报 `ClearCommError`。

**原因.** 串口被别的程序占着(IDF monitor 没退、串口助手还开着),或者插的是另一个 USB-C 口。

**处理.**
- 先关掉所有占用串口的程序;
- 确认插的是带 USB 转串口芯片的那个口;
- 监视波特率 **115200**;
- 两个 USB-C 口对应的设备名不一样,记住哪个是哪个。串口名以系统实际枚举为准,
  换个 USB 口编号就会变。

**已核对的版本.** ESP-IDF **6.1.1**,`esptool` 随 IDF 自带。文档里分别写清版本、
两个口对应的设备、应用烧录(`app-flash`)和串口查看(`monitor`),避免混着做。

## 4. 舵机能转,但按键和复位的重复性不够

**现象.** 连续旋转 SG90 在测试里能正反转。早期版本下压后没有回到预期位置;
相同的运行时长,往两个方向走出来的实际行程也可能不一样。

**原因.**
- 连续旋转舵机**没有位置反馈**,固件只能按时间估算行程,不知道自己现在在哪;
- 调过一次的位置会被安装间隙、负载、供电电压影响;
- 两个方向的转速本身可能不对称。

**现在的方案(2.6).**
- 下压和回位**分开设置**,每项 5°–180°,下压后**停转 3 秒**再回位 ——
  停下来这段时间让键帽被稳定压下,也让机械结构有时间回弹;
- 手机首页和磁贴共用同一套设置;
- 串口 `a ±角度` 可以微调起点,不必反复重新烧录。

**没解决的部分.** 仍然需要按实际安装结构验证「按到 / 松开 / 连续多次」。
10 轮连续按压的成功率和回位偏差还没测,见 [`test-results.md`](test-results.md)。

## 5. Windows 到了登录界面,远程桌面却不上线

**现象.** 测试机在**普通锁屏**状态下能远控;但**冷启动停在登录界面**时,按原配置通常要等
输入密码之后才上线。

**怎么判断的.** 系统服务已经在会话 0 里运行,但「服务在跑」不等于「登录前就能远控」。
远控客户端本身要有个能在登录会话之外启动的进程。

**现在的方案.** 在测试机上给远控启动器加一个 **SYSTEM 身份的开机计划任务**,
延迟 30 秒启动、不限运行时长。这样登录界面出现之前远控就已经起来了。
脚本和还原方法见 [`windows-prelogon.md`](windows-prelogon.md)。

**没解决的部分.** 只在**一台 Windows 10 测试机**上验证过登录前可连接。
Windows 11 的登录前联网和远控自启要**逐台**分别记录,不能假设一样。

## 6. 断电重连和省电要一起验证

**现象 / 关注点.** C5 长期待命,重启后必须回到**同一个**设备命令主题,否则手机会发给一个没人收的主题。
早期公网诊断还依赖用户手动输入联调码,很容易和正式通道的配置搞混。

**现在的方案.**
- 正式通道用固定主题前缀(存在 `menuconfig` 里,不随机生成);
- Wi-Fi 用 `WIFI_PS_MIN_MODEM`,兼顾待机功耗和响应;
- 联调码和正式前缀彻底分开:诊断走 `c5-link/<设备ID>/ping|pong`,开机走 `<前缀>/cmd`;
- 2.6 烧录后已观察到断电重启能自动联网并完成正式 MQTT 订阅。

**还要重复验证的.** 断电自动恢复的耗时、离线状态显示是否及时、重启期间发出的新指令能否可达、
断电前的旧指令是否一定不执行。见 [`test-results.md`](test-results.md)。

## 附:诊断时优先看的几行日志

| 日志 | 含义 |
|---|---|
| `Connecting to <ssid>` | 开始连 Wi-Fi |
| `MQTT subscription acknowledged` | 订阅成功,板子开始收指令 |
| `Phone MQTT ready (ping/pong)` | 诊断通道就绪 |
| `Phone MQTT: ping received, pong queued` | 收到手机 ping 并入队 pong |
| Wi-Fi `reason=23` | 关联被 AP 拒绝,认证/频段问题 |
| `MQTT error type=... TLS error=...` | TLS 握手或证书问题 |
| `UART: a <signed degrees> + Enter` | 串口调试入口就绪 |
